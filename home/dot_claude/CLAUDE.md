# エージェントインストラクション

## 基本方針

- 作業前のコンテキスト読み取りでは、*_ja.mdに一致するファイルを除外し、それ以外のすべてのファイルを読み取ります。
- 英語で思考しますが、通常の出力は日本語です。コミットメッセージと、MITライセンス時のコメントおよびドキュメントは下記の規則に従います。
- 作業開始時にリポジトリのライセンスを最初に確定します。ライセンスが不明な場合はユーザーに1回だけ確認し、その結果をコミット言語・ドキュメント言語・_ja.md作成・コメント言語のすべてのライセンス依存ルールに適用します。
- ユーザーから指定がある場合を除き、アプリケーションは初期開発段階にあるため、後方互換性やデータ移行を考慮する必要はありません。
- 設計ファイルがある場合は設計先行型で開発し、常に設計内容をユーザーと協議し、確定してから実装してください。実装後に仕様変更が生じた際も設計書の変更（再設計）からスタートしてください。
- 与えられたタスクのスコープを勝手に狭めたり、指示されていない MVP を独自に定めたりしないでください。
- サブエージェントを使って、計画→実装→検証→再計画のループを自律的に回してください。与えられたタスクがすべて完了するまで、作業を終了しないでください。
- UI のレイアウト設計では、安直にデータモデルのプロパティを並べるのではなく、データモデルとユースケースから UI が提供すべき情報構造を設計し、必要十分な情報を適切なタイミングで画面に表示してください。
- UI が関係する実装では、スクリーンショットなどで実際の表示を確認し、合否を判定してください。
- 常にタスクを細分化し、サブエージェントや複数のセッションを用いた並列実行を検討してください。

## 作業方針

### リモートがGitHub の場合

- /plan で作業が承認された後、issueを作成します
- /planによる承認なしに直接作業を依頼された場合は、まず/planに相当する計画をユーザーに提示して承認を得てからissue/Work Itemを作成します。
- /plan で複数段階のタスクがある場合は、issue作成後にsub-issueへ分割する前提で計画します。sub-issueの実作成はissue作成後に行います。コミットはissue単位で行います。
- issue作成後、トピックブランチを作成してから計画を開始します。
- issue作成後、issueに含まれるタスクが3つ以上、または想定ファイル変更が5ファイルを超える場合は、作業開始前にsub-issueを作成します。
- issueのタイプの中から適切なラベルを選択する。複数つけてもよい

### リモートがGitHub・Azure DevOps以外の場合（またはリモートなし）

- issueやWork Itemは作成せず、ブランチ名ルールとコミットメッセージルールのみ適用します。
- リモートなし、またはGitHub・Azure DevOps以外の場合、ブランチ名のissue番号部分は省略し、`prefix/説明`の形式を使用します。例: `feature/add-login-page`

### リモートがAzure DevOpsの場合

- /planで作業が承認された後、作業開始前に Work Itemを作成します。
- Work Item作成後 Topic Branchを作成します。
- `epic`, `product backlog`, `task`, `user story`は生成したplanに基づき生成し、ユーザーに確認します
- 作業内容のキーワードや機能領域が既存の`epic`, `product backlog`の説明と一致する場合、ユーザーに候補一覧を提示して選んでもらいます。ユーザーが新規作成を選んだ場合はplanモードを推奨して、確認してもらいます。
- バグの場合は`bug`を使用します。
- 作業前にwork itemの`state`を`doing`に設定します。作業者を自分に設定します。

### ドキュメント内のスクリプト

- bash(macOS/Linux)とPowerShell 7用のスクリプト両方作ります。Azureのコマンドを例示で作る場合、Azure CLIを前提にします。

### コミットメッセージ

- コミットメッセージの言語は次の順で判断します。
  1. リポジトリがパブリックの場合は英語
  2. リポジトリがプライベートかつライセンスがMITの場合は英語
  3. リポジトリがプライベートかつライセンスがMIT以外またはライセンスなしの場合は日本語
  4. ライセンスが不明な場合は作業開始前にユーザーへ確認
  5. 上記以外の条件は日本語
- 以下のメッセージルールに従ってください。
  - 機能追加は add
  - バグ修正は fix
  - 更新は update
  - 削除は remove

```
[add/fix/update/remove]: [description]
```

### ブランチ名ルール

ブランチ作成は以下のprefixをつけます。

- 新機能作成時: feature/issue番号（Azure DevOpsの場合はWork Item ID）-
- バグ修正: fix/issue番号（Azure DevOpsの場合はWork Item ID）-
- リファクタリング: refactor/issue番号（Azure DevOpsの場合はWork Item ID）-
- 性能改善: perf/issue番号（Azure DevOpsの場合はWork Item ID）-
- パッケージ更新やtypo修正: chore/issue番号（Azure DevOpsの場合はWork Item ID）-
- ソースコード以外の修正: docs/issue番号（Azure DevOpsの場合はWork Item ID）-

### 作業に関する記録

- `docs/task.md`があった場合、作業終了時に、作業内容を記録します。作業内容の記録は、作業開始時に作成したplanに基づき、作業内容を記録します。作業内容の記録は、ユーザーが確認できるように、issueやWork Itemにリンクを貼ります。
- 実装計画立案時、当初の`docs/task.md`, `docs/plan.md`にない仕様変更があった場合、`docs/adr.md`に日付、該当taskと仕様変更の理由を箇条書きで記録します。`adr.md`が200行を超える場合、phase単位で分割します。
  - 仕様を変更する必要がある場合、必ず`adr.md`を確認して、変更理由が以前の修正と矛盾しないか確認します。矛盾しそうな場合はユーザーに承認を求めます。
- 実装計画のmarkdownはリモートレポジトリがAzure DevOpsもしくはGitHubであった場合、Wikiに登録します。登録前にユーザーに確認してから登録します。IPアドレス、URL、メールアドレス、GUIDなどの識別可能な情報はWikiに登録しません。
  - Azure DevOpsの場合、チームプロジェクトのWikiにのルートにレポジトリ単位のサブページを作り、その中にレポジトリ単位でplanが作成したmarkdownを登録します。planごとにmarkdownをwikiに登録します。
  - GitHubの場合、Wikiのルートに`plan`というサブページを作り、その中にレポジトリ単位でplanが作成したmarkdownを登録します。planごとにmarkdownをwikiに登録します。

## 補足

- リモートがGitHubの場合、ライセンスがない場合、MITライセンスでいいか確認してから始めます。
- ユーザーがMIT以外のライセンスを選択した場合、ドキュメントは日本語で作成し、_ja.mdファイルは作成しません。選択されたライセンスファイルを生成してから作業を開始します。
- SECURITY.mdがない場合、英語で作成します。最低限、脆弱性の報告方法（連絡先はプレースホルダにする）とサポート対象バージョンの記載を含めます。
- MITライセンスの場合、ソースコードのコメントおよび、ドキュメントは英語で作成します。日本語版が必要な場合はfile baseの最後に `_ja`をつけたmarkdownを作成します。たとえばreadme_ja.mdです。ただし、SECURITY.mdやLICENSEに関するファイルにはこのルールを適用しません。

## 禁止事項

- GitHubのWiki以外、URLやIPアドレスはissueやドキュメントに書かない。必ずプレースホルダにする。ソースコードやスクリプト中にプレースホルダにした場合、置換するスクリプトも用意する
- SECURITY.mdやLICENSEに関するファイルを日本語で作らない
