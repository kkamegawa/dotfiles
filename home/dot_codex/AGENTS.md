# エージェントインストラクション

## 基本方針

- 作業前に、適用される指示と依頼に直接関係するファイルを読み取ります。参照先・依存関係・検証結果に応じて読み取り範囲を広げ、無条件に全ファイルを読み取ることはしません。`*_ja.md`は通常の事前読み取りでは除外しますが、翻訳の整合性確認や日本語文書の変更が依頼に含まれる場合は対象として読み取ります。
- 英語で思考しますが、通常の出力は日本語です。コメント・ドキュメント・_ja.md・コミットメッセージの言語は、次の表に従います。
- 作業開始時にリポジトリのライセンスを最初に確定します。ライセンスが不明な場合はユーザーに1回だけ確認し、その結果を上記の表に基づいて言語ルールを適用します。

  | 条件 | コメント | ドキュメント | _ja.md | コミットメッセージ |
  | --- | --- | --- | --- | --- |
  | MITライセンス | 英語 | 英語 | 作成する | 英語 |
  | MIT以外のライセンス | 日本語 | 日本語 | 作成しない | 日本語 |
  | SECURITY.md / LICENSE関連 | 英語 | 英語 | 対象外 | - |

- ユーザーから指定がある場合を除き、アプリケーションは初期開発段階にあるため、後方互換性やデータ移行を考慮する必要はありません。
- 設計ファイルがある場合は設計先行型で開発します。新規仕様または仕様変更が必要な場合は、設計内容をユーザーと協議し、確定してから実装してください。承認済みの設計・作業範囲に沿う実装と検証では、同じ内容の再確認を求めません。実装後に仕様変更が生じた際も設計書の変更（再設計）からスタートしてください。
- 設計書はあるべき姿の最終形態を表します。過程のメモ書きは禁止です。
- 与えられたタスクのスコープを勝手に狭めたり、指示されていない MVP を独自に定めたりしないでください。
- 実装が依頼された場合は、承認済みの範囲で計画→実装→検証→再計画のループを自律的に回し、必要な作業が完了するまで継続してください。調査・レビューのみの依頼は、結果の報告をもって完了とし、実装へ進めません。
- UI のレイアウト設計では、安直にデータモデルのプロパティを並べるのではなく、データモデルとユースケースから UI が提供すべき情報構造を設計し、必要十分な情報を適切なタイミングで画面に表示してください。
- UI が関係する実装では、スクリーンショットなどで実際の表示を確認し、合否を判定してください。
- タスクを分割し、独立した調査・実装・検証を並行して進められる場合、またはユーザーが指定した場合にサブエージェントを使ってください。短い変更や順序依存の強い作業では、分割の負担を考慮して単独で進めます。並行編集では担当ファイルを分け、同一ファイルの変更が必要な場合は編集順序を調整してください。
- モードによってツールが制限されている場合は回避方法を探さずに、素直にユーザーにモードの変更をリクエストしてください。

## 依頼の範囲

- 「調査だけ」「レビューのみ」などの指定がある場合は読み取り専用で進め、ファイル変更、コミット、Issue・Work Item・Wikiの作成や更新を行いません。LICENSEやSECURITY.mdの不足は報告し、作成・変更しません。
- ユーザーが許可した実装・検証・外部更新は、その範囲で継続してください。すでに得た許可を繰り返し求めません。
- 依頼の範囲を超える仕様変更や外部更新が必要になった場合は、必要性と対象を具体的に示して確認してください。

## ドキュメント作成

docs/ 以下のADR・アーキテクチャ・インフラ・テスト・セットアップ文書は project-documentation スキル（marketplaceのtfsugjp/skills）の手順と承認ゲートに従います。ただしスキルの「正本は英語」という既定は、本ファイルのライセンス別言語表を優先します（MIT以外のライセンスでは日本語を正本とし、`_ja.md`は作りません）。

## 作業方針

- ファイル変更を含む作業では、既存の関連IssueまたはWork Itemを確認し、利用できる場合は再利用します。新規作成が必要な場合は、marketplaceのtfsugjp/skillsのskillを使用して、Azure BoardsではWork Item、GitHubではIssueを作成します。調査・レビューのみの依頼では、作成・更新しません。
- ファイル変更を含む作業の実装計画は、ユーザーが内容を確認・承認してから、marketplaceのtfsugjp/skillsのskillを使用してWikiに登録してください。すでに同じ範囲の計画が承認されている場合は再確認せず、その計画を使用します。GitHubの場合のみ日本語と英語のplanを登録します。調査・レビューのみの依頼ではWikiを更新しません。

### Gitリモートレポジトリなしの場合

- issueやWork Itemは作成せず、ブランチ名ルールとコミットメッセージルールのみ適用します。
- リモートなし、またはGitHub・Azure DevOps以外の場合、ブランチ名のissue番号部分は省略し、`prefix/説明`の形式を使用します。例: `feature/add-login-page`

### ドキュメント内のスクリプト

- bash(macOS/Linux)とPowerShell 7用のスクリプト両方作ります。Azureのコマンドを例示で作る場合、Azure CLIを前提にします。

### sandboxでのgit/gh

- 認証が必要な`gh`と`git`(push/fetch/pull/clone/ls-remote)は、sandbox外で実行する`excludedCommands`で許可しています。この除外はコマンドの先頭一致のため、`cd ... && gh ...`や`echo ...; gh ...`のように前へ別のコマンドを付けたり、パイプや連結で他のコマンドと1行にまとめたりすると、sandbox内で実行されて失敗します(ghの起動拒否、GCMのクラッシュ)。これらは必ず単独のコマンドとして実行してください。

### 作業に関する記録

- ファイル変更が依頼の範囲に含まれ、`docs/task.md`がある場合は、作業終了時に承認済みのplanに基づく作業内容と検証結果を記録します。関連IssueまたはWork Itemがある場合はリンクを貼ります。調査・レビューのみの依頼では、`docs/task.md`を変更しません。
- 当初の`docs/task.md`, `docs/plan.md`にない仕様変更が生じた場合のADR記録は、project-documentationスキルの手順（`docs/adr/`以下、承認ゲート・変更履歴）に従います。
- 実装計画のWiki登録は、上記の「Gitリモートレポジトリありの場合」に従います。GitHub・Azure DevOps以外のリモートには、個別の指示がない限りWiki登録を行いません。

## 補足

- GitHubがリモートでなおかつ、ライセンスがない場合、一度だけMITライセンスでいいか確認してから始めます。
- ユーザーがMIT以外のライセンスを選択した場合は、上記の表の「MIT以外のライセンス」に従って作業を進めます。選択されたライセンスファイルを生成してから作業を開始します。
- SECURITY.mdがない場合は、上記の表の「SECURITY.md / LICENSE関連」に従って英語で作成します。最低限、脆弱性の報告方法（連絡先はプレースホルダにする）とサポート対象バージョンの記載を含めます。
- MITライセンスの場合は、上記の表の「MITライセンス」に従って作業を進めます。日本語版が必要な場合はfile baseの最後に `_ja`をつけたmarkdownを作成します。たとえばreadme_ja.mdです。

## 禁止事項

- URLやIPアドレスをissueやドキュメントに書かない。必ずプレースホルダにする。ソースコードやスクリプト中にプレースホルダにした場合、置換するスクリプトも用意する。Wiki内のissueおよび、認証なしでアクセス可能なURLはプレースホルダにしない。
- SECURITY.mdやLICENSEに関するファイルを日本語で作らない。
